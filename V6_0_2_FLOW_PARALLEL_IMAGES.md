# v6.0.2 — Flow parallel-image reliability

## What this fixes

- Parallel per-shot image candidates now run in genuinely separate worker lanes: each lane has its own persistent profile (or a dedicated tab in an already-authenticated CDP/Windows Chrome session) and its own named Flow project. Previously, workers could navigate the same CDP tab and share one Flow project's new-asset list, making concurrent requests interfere with exact tile identity checks.
- Candidate-to-worker assignment is stable across Resume, so a pending image's saved project binding stays with the same worker when other candidates have already completed.
- When recovering an already-generated image, the browser now polls the recovered project gallery for up to 15 seconds for the **recorded signature**. It will not substitute a different tile. Browser closure remains a recovery error, not evidence that an asset is missing.
- Existing ordinary-error free-image fallback is preserved and recorded in job logs. A saved/pending Flow request is never sent to the free provider or regenerated by the parallel fallback.

## Scope of the worker setting

`Parallel Flow image workers` controls per-shot candidate-image generation in the Flow profiles that enter that stage. It does not parallelize the **Storyboard Economy** continuity-frame pipeline: that profile creates character/location masters first and then builds scene opening/closing frames in continuity order. The dashboard now disables the worker control for Storyboard Economy rather than implying it applies there. Worker count remains bounded to 1–3; Flow may throttle simultaneous sessions, so start with 1.

The log provided for job `20261002-090603-naughty-lord-ganesh-play-8f6c` stopped at `character_master.jpg`, before the per-shot parallel-candidate queue. That failure was in the serial master-image stage, not in a parallel worker. The improved exact-signature gallery wait helps with its recorded-image recovery, but the user still needs to retry/resume the job to verify authenticated Flow behavior.

## Upgrade an existing WSL installation

1. Stop Streamlit (`Ctrl+C`) and back up the current folder.
2. Extract the v6.0.2 ZIP to a new folder.
3. Copy your current `outputs/` (including job-local `.flow-workers` folders, if present), `data/`, `.env`, `config/user_settings.yaml` if present, and browser profiles into the new installation. These can contain private session data; keep them private and do not replace them with the ZIP's examples.
4. In the existing job's settings, use `flow_image_workers: 1` initially; raise to 2 or 3 only after one complete run works. Restart with `./dashboard.sh`, select the existing job, and Resume it once.
5. Do not create a duplicate job to bypass a pending image record. Keep the `.flow-request.json` and recovery diagnostics with the job.

## Validation and limits

- Regression suite: **470 passed, 5 skipped**; Python compileall passes.
- Tests verify two Flow workers actually overlap, use distinct projects, use distinct CDP tabs without closing the user's tab, preserve a candidate's worker assignment when another candidate is resumed, never replace a pending Flow request with free output, and wait for the exact recorded image before downloading.
- No live authenticated Google Flow browser/WSL session is available in this environment. The suite validates orchestration and safety behavior, not Google's current UI, account limits, or real multi-session throughput. Parallel workers can still be throttled by Flow.
